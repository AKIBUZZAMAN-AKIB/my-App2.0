## Decision log

- D1 (Phase 1): a rewind that cuts inside the summarized range resets the summary (as a version, revertible) instead of trying to recompute it; archived turns before the cut are kept. Safest, reversible, matches ADR-6.
- D2 (Phase 1): `write_tx` was introduced in Phase 1 (atomic reset/rewind need composable transactions) and is reused for the Phase 2 IMMEDIATE work.
- D3 (Phase 1): the earlier list fields (`facts`, `preferences`, `files`, `openItems`) stay in the JSON as a mirror of current items so older builds and the existing UI keep working (additive, no migration needed); `items` is authoritative when present.
- D5 (Phase 2): migrations are additive only (new tables `memory_meta`, `turn_memory_quarantine`); no column is dropped or retyped, so an older build still opens the DB (ADR-9). The schema number is never lowered.
- D6 (Phase 2): an unreadable memory with no readable history is summarized again from the transcript (the source of truth) instead of blocking memory forever; the unreadable JSON is preserved in `turn_memory_quarantine`, so nothing is lost.
- D7 (Phase 3): the original is carried by a task-local scope + a private result field rather than changing `execute_tool`'s signature, so every other caller (sub-agents, host APIs) is unchanged and gets no extra memory use. Default ceiling 8 MiB per output (ADR-7), user-configurable.
- D4 (Phase 1): items carried over from the earlier list format whose turn is unknown keep an empty `sourceTurns` rather than a guessed turn.
- D8 (Phase 4): background summaries run in-process on the existing Tokio runtime only. Android WorkManager stops a worker after about 10 minutes and the OS may stop it at any time; iOS `BGProcessingTask` gets an expiration handler and no guaranteed start. A model call that may take minutes and must hold a lease fits neither as the primary path; jobs are durable, so a killed process loses nothing: the lease expires / startup recovery re-queues, and finished portions are reused.
- D9 (Phase 4): `backgroundSummaries` is off by default (plan: "behind a setting"); turning it on needs no migration and turning it off cancels the queued job and returns to the synchronous path. Flip the default after a real-provider check.
- D10 (Phase 4): jobs are planned from the stored transcript (source of truth), never from the in-memory turn, and verified by `input_hash` again before the model call; a rewind/edit makes a job `superseded`, never committed. The batch the turn sees and the stored one can differ only by the turn in flight, which is never part of a batch.
- D11 (Phase 4): backoff = exponential (base 10 s, cap 15 min, 5 attempts) with equal jitter. AWS's simulation found Full Jitter slightly cheaper ("Equal Jitter is the loser"), but that measures many clients competing for one resource; here one device retries one provider, and equal jitter keeps at least half the delay so a retry never fires almost at once after a rate-limit error; the jitter is a hash, not a random number, so tests are deterministic and no `rand` dependency is added.
- D12 (Phase 5): the turn index is derived from `messages` on every read, not stored in a `turn_index` table as the plan sketched. `save_session` rewrites the whole transcript, so a stored index would need its own invalidation and is exactly the kind of second copy that caused W-2. Splitting is linear and cheap next to a model call; an index table can be added later as a cache keyed by the transcript hash without changing callers.
- D13 (Phase 5): reads use the transcript first and the archive only as fallback; when both exist and differ, the transcript is used and the difference is reported, never silently merged.
- D14 (Phase 5): recall keeps the 12-portion and 200-turn budgets (cost control) but reports every cut range with the exact follow-up call, instead of raising the limits.

## Research (Phases 4-7), primary sources read in this run

Phase 4 (durable background jobs)
- Tokio `spawn` (docs.rs/tokio/latest/tokio/task/fn.spawn.html): "There is no guarantee that a spawned task will execute to completion. When a runtime is shutdown, all outstanding tasks are dropped." → the in-process worker can never be the only record of work; the job row is. Applied: durable `memory_jobs`, lease + startup recovery.
- Tokio `Notify` (docs.rs/tokio/latest/tokio/sync/struct.Notify.html): "A Notify value contains a single permit … If notify_one() is called multiple times before notified().await, only a single permit is stored." → a wake-up sent while the worker is busy is not lost, and many wake-ups collapse into one. Applied: worker wake signal.
- Amazon SQS visibility timeout (docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html): a received message "remains in the queue but becomes temporarily invisible to other consumers … ensures that other consumers cannot process the same message while you are working on it"; long tasks extend it. Applied: `lease_until` + heartbeat; an expired lease makes the job claimable; the lease must still be held in the commit transaction.
- Stripe idempotent requests (docs.stripe.com/api/idempotent_requests): "use an idempotency key. Then, if a connection error occurs, you can safely repeat the request without risk of creating a second object." Applied: `job_key` derived from the batch range and input hash; enqueue is a no-op for an existing key.
- AWS Architecture Blog, "Exponential Backoff and Jitter" (aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/): compares Full, Equal and Decorrelated jitter; Equal Jitter "prevents very short sleeps, always keeping some of the slow down". Applied with the trade-off in D11.
- Android WorkManager, define work (developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work): backoff delay "can be no less than 10 seconds (MIN_BACKOFF_MILLIS)"; default policy EXPONENTIAL. Applied: base delay 10 s, exponential.
- Android WorkManager, long-running workers (…/persistent/how-to/long-running): long-running workers "can run longer than 10 minutes" only by running a foreground service. → a regular worker is time-limited. Applied: D8 (no OS job as the primary path).
- Apple `BGProcessingTask` (developer.apple.com/documentation/backgroundtasks/bgprocessingtask): "Although processing tasks can run for minutes, the system can interrupt the process … Processing tasks run only when the device is idle. The system terminates any background processing tasks running when the user starts using the device." `expirationHandler`: "may be called before the background process uses the full amount of its allocated time." Applied: D8.
- SQLite partial indexes (sqlite.org/partialindex.html §2.1): a UNIQUE partial index enforces "uniqueness across some subset of the rows in a table". Applied: `memory_jobs_one_active` (one queued/running job per chat, enforced by the DB).
- SQLite transactions (sqlite.org/lang_transaction.html): "IMMEDIATE causes the database connection to start a new write immediately … might fail with SQLITE_BUSY if another write transaction is already active." Applied: every claim/heartbeat/fail/commit runs in `write_tx` (BEGIN IMMEDIATE), so two workers never both see a job as free.
- SQLite UPSERT (sqlite.org/lang_upsert.html): `ON CONFLICT … DO UPDATE … WHERE`. Applied: conditional revival of cancelled/superseded/old-failed jobs in one statement.
- LangGraph checkpointers (from the Phase 0 research, MEMORY_RESEARCH.md): "pending writes" of finished nodes are kept so a resumed run does not redo them. Applied: `memory_job_parts`.


Phase 5 (source-grounded recall)
- Gao et al., "Enabling Large Language Models to Generate Text with Citations" (ALCE), arXiv:2305.14627: proposes "automatic metrics along three dimensions — fluency, correctness, and citation quality"; even the best models lack complete citation support about half of the time on ELI5. → citations must be checked by code against the original text, not trusted. Applied: recall/repair evidence is verified against `load_source_turns` (transcript), unread/missing turns are stated by code, not by the model.
- Liu et al., "Lost in the Middle" (arXiv:2307.03172, in MEMORY_RESEARCH.md): models use the middle of long contexts poorly. Applied: recall keeps small portions and reports what it skipped rather than stuffing more turns into one call.
